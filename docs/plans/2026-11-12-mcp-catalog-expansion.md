# MCP catalog expansion

## Repository assessment

- Extension activation builds `McpHost`, reads only user-scoped `sovran.mcp.servers`, loads credentials from VS Code SecretStorage, and updates `McpHub` in the background. Enabled entries start in trusted windows. The host serializes settings writes and keeps malformed settings entries in place.
- `core/mcp/config.ts` uses a single server record with an ID, enabled flag, command/args/env/cwd or URL/headers, authentication placement, timeout, and per-tool Off/Ask/Allow policies. Managed entries add preset ID, version, and profile. Plain headers, arguments, and environment settings are visible in settings.json. SecretStorage supports one credential per server ID, delivered as a bearer token, named header, or environment variable. There is no MCP OAuth client flow.
- `NodeMcpTransports` resolves variables, checks stdio executables, and creates the official SDK stdio or Streamable HTTP transport. `McpHub` initializes the client, discovers tools, listens for supported list changes, and reports Connected after initialization and discovery. The transport closes child processes and attempts HTTP session termination on disconnect. Generations invalidate old callbacks and stale definitions. Connection startup allows 120 seconds. Calls have a configurable timeout, cancellation, and a total progress cap. An error leaves manual retry available.
- Tools enter the same registry and execution pipeline as native tools. They are available only in trusted Act mode, subject to per-chat groups and live permission checks before dispatch. Per-server namespacing plus hashing handles invalid and long tool names. Collisions are skipped. Managed allowlists constrain both discovery and dispatch. Tool descriptions and schemas are untrusted. Existing bounds and approval controls reduce their impact but cannot establish their intent.
- The existing registry already describes pinned Playwright and Chrome DevTools packages and hosted GitHub. Managed browser installs require a separate explicit action and run locked npm installs with scripts disabled. The host checks Node.js and system Chrome at launch. GitHub uses a PAT and a read-only or collaboration profile. `McpSettings.tsx` has a selection-first catalog and a separate custom form with JSON import. Creating a custom entry currently starts it when the workspace is trusted.
- SOVRAN has native file search, text reads and edits, Git, diagnostics, and public Web fetch. Its native agent tools do not expose VS Code symbol definitions and references. Its workspace-scoped conversation storage saves session JSON and an index, with global fallback for no-folder windows. It is independent of external MCP state.

### Context7

The hosted endpoint adds version-aware documentation lookup with two tools and zero runtime setup. Anonymous users are rate-limited. At review, the free keyed tier covers public repositories and 1,000 calls per month with 20 daily bonus calls after the limit. Private repo parsing is paid. Keep a key optional and offer SecretStorage for quota or authentication failures. Limit the managed profile to library resolution and documentation lookup. The open-source adapter calls the Context7 API, so local execution still sends the library and query to the service. The hosted endpoint also avoids redistributing or installing the npm package. [License](https://github.com/upstash/context7/blob/master/LICENSE), [MCP setup](https://context7.com/docs/resources/all-clients), [local adapter](https://context7.com/docs/resources/developer), [API and limits](https://context7.com/docs/api-guide), [plans](https://context7.com/plans), [API client source](https://github.com/upstash/context7/blob/master/packages/mcp/src/lib/api.ts)

### Serena

Symbol lookup, references, and symbol-level editing add capabilities beyond SOVRAN's text search and file edits. They overlap with language intelligence that VS Code already runs for the editor. Serena typically launches its own language servers or connects to a JetBrains plugin. Python, JavaScript/TypeScript, Go, Rust, Java, C/C++, C#, Ruby, PHP, and other languages are covered with different prerequisites and maturity. A second index, language-server processes, caches, and first-use downloads add startup, CPU, disk, and memory overhead. The size of that overhead depends on the project and was not benchmarked. A manually installed custom server is appropriate for users who need agent-facing symbol operations now. A featured preset would need a reviewed tool profile, a workspace-selection policy, and per-language dependency checks. [License](https://github.com/oraios/serena/blob/main/LICENSE), [Python manifest](https://github.com/oraios/serena/blob/main/pyproject.toml), [installation](https://oraios.github.io/serena/02-usage/010_installation.html), [running](https://oraios.github.io/serena/02-usage/020_running.html), [language support](https://oraios.github.io/serena/01-about/020_programming-languages.html)

### DBHub

PostgreSQL, MySQL, MariaDB, SQL Server, Oracle, and SQLite are supported. DBHub accepts a DSN from the environment or a TOML file that references environment variables. The reviewed v1.6.1 release includes read-only and EXPLAIN fixes. Its unpacked upstream MCP bundle provides an explicit read-only TOML and row limit, and the existing custom secret environment field can supply its `DBHUB_DSN`. The database must still enforce least privilege. Query results can include secrets or personal data even when every query is read-only. Keep SQL on Ask and use a dedicated database account scoped to safe schemas or views. A writable profile would require operation-specific confirmation, including during Auto mode. A managed preset needs real driver and read-only rejection tests, a pinned reviewed artifact, and controls that keep credentials out of process arguments and configuration files. The DBHub artifact and its database behavior were reviewed in upstream sources. Live driver and write-rejection tests remain a gate for a managed preset. [License](https://github.com/bytebase/dbhub/blob/main/LICENSE), [installation](https://dbhub.ai/installation), [transport and DSN](https://dbhub.ai/config/command-line), [read-only tools](https://dbhub.ai/tools/execute-sql), [bundle](https://dbhub.ai/mcpb), [v1.6.1](https://github.com/bytebase/dbhub/releases/tag/v1.6.1)

### Memory

Memory is an actively updated reference server, with server-memory 2.1.1 published in the November 2026 release. It stores entities, relations, and observations in JSONL. Atomic replacement and file locking protect writes on suitable local filesystems. The default path sits inside the installed package and can disappear on cache cleanup. Use an absolute `MEMORY_FILE_PATH` in an existing private directory for persistence, and choose a different path for each workspace. Users can inspect the file or query the graph and delete entities via tools. To remove the entire store, stop clients sharing it and delete the file. Chat deletion does not delete that graph. Native project memory would let SOVRAN own workspace identity, inspection, deletion, and retention across sessions. That is a better default than a second agent-managed store. [Memory docs](https://github.com/modelcontextprotocol/servers/tree/main/src/memory), [package manifest](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/package.json), [releases](https://github.com/modelcontextprotocol/servers/releases), [repository license](https://github.com/modelcontextprotocol/servers/blob/main/LICENSE)

## Implementation plan

1. Extend `catalog.ts` with hosted endpoint, credential metadata and reviewed tool allowlist. Keep package versions and lockfiles for the existing browsers. Share hosted connection validation across GitHub and Context7. Preserve existing settings and protocol shapes.
2. Use a single Browse Catalog list with local/remote labels and live states. Show prerequisites and credential requirements beside each option. Put browser/access alternatives and command inspection under advanced settings. Keep Custom MCP Server and JSON import in the same Integrations area. Use the existing VS Code theme colors, system typography, left-aligned rows and status dots so the catalog stays legible in a narrow sidebar.
3. Save new custom entries disconnected, prompt before starting local commands, and keep existing enabled settings compatible. Preserve the shared transport and tool pipeline. Verify current connection state and discard stale work when restart and disable overlap.
4. Test hosted settings, optional bearer placement, profile filtering, stale tool rejection, consent, and catalog status with existing fixtures. Run typecheck, lint, tests, and production build. Update README, architecture, and user guide.
5. Keep future tool search or Code Mode at the registry boundary. The same authorization and execution checks must run on every call. Use managed allowlists and per-chat exclusions to limit tool definitions today. Measure aggregate schema cost before introducing dynamic discovery.

## Validation

- `npm run check` passed typecheck, lint, and 650 tests across 34 files. The two opt-in managed browser tests were skipped. Local stdio and loopback Streamable HTTP fixtures exercised discovery, tool calls, missing executables, authentication, redirect isolation, and disconnect behavior.
- `npm run build` and `git diff --check` passed. The real VS Code 1.145.2 smoke suite passed on macOS arm64. The built catalog was visually checked at a 320px sidebar width in headless Chrome with VS Code theme variables.
- The installed MCP SDK initialized against the live Context7 endpoint with no credentials, discovered `resolve-library-id` and `query-docs`, and returned text for a public React documentation query. The optional bearer path was tested against a loopback server. Live authenticated Context7 and GitHub calls, DBHub and Serena processes, and Windows/Linux/Remote hosts remain unverified.
